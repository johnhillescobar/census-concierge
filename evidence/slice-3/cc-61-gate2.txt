Pass 1 — generic bugs
code only; no knowledge of intent
==============================================================================

1. combine_additive sums every row as an area, including year copies
   fetch_data already concatenates year-tagged rows (`item["year"] = str(year)`).
   combine_additive walks the whole list and RSS-sums any E/M pair with no
   partition on `year` or GEO_ID. A combine-intent question whose fetch also
   fanned years (N areas × Y vintages) reports `combined (N*Y areas)` and a
   total that is the sum of vintages, not of areas. The appended row looks
   like a correct combined estimate.

2. combined row has no GEO_ID
   assemble runs _rows_with_geoid, then finish_aggregation appends the
   combined dict. That dict sets NAME / MOE_formula / component_count and
   the E/M totals; it never sets GEO_ID. _moe_rows therefore emits a last
   moe object without GEO_ID either. contract.py still says each row carries
   GEO_ID. ARCHITECTURE.md still says assemble "puts AFFGEOID GEO_ID on
   every row." Tests assert "GEO_ID" not in combined.

3. component_count is a union across variables
   contributing is a set of row indexes that had a valid E+M pair for any
   estimate key. Each key's sum/RSS uses only that key's pairs. One variable
   can be summed over 2 rows while NAME says combined (6 areas).

4. any non-median E/M pair is treated as additive
   _median_measure is the only skip. Rate, percent, mean, per-capita, and
   other derived measures that match _COMBINE are summed and RSS-combined
   the same way as counts.

5. _COMBINE matches the word "combined" anywhere
   `\bcombined\b` fires on "combined statistical area" (and similar). A
   multi-row fetch for that question gets a combined row it did not ask for.
   Single-row fetches are unaffected (len(pairs) < 2).

6. B19001 is hardcoded on every median-combine warning
   median_not_aggregatable.detail always names B19001 household-income
   brackets. finish_aggregation always injects Alternative(B19001) when that
   warning fires and the pool did not already list it. Selected table can be
   some other median (age, rent, …).

Nothing else on this pass. No crash, no uncaught None on the new path, no
double-append of the combined row, no numbers routed through the model.

Most important reason first: combine_additive sums fetch_data's year-tagged
row list as if every row were a distinct area, so a combine-intent series
fetch silently reports a multi-vintage total as a combined-area estimate.

Other findings (do not ship around the one above):
- combined row omits GEO_ID while the contract and ARCHITECTURE.md say
  every row carries it
- component_count can overstate how many areas entered a given variable
- non-median derived measures (rates, percentages, means) are summed
- `\bcombined\b` matches "combined statistical area"
- B19001 is injected for every median-combine, not only household income
