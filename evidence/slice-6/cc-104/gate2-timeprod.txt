G1 [PASS-1, CONFIRMED] A year the user asked for is silently replaced by the latest vintage whenever the split report does not carry it.
   api/src/finish.py:369 (`{"years": intent.years}`), api/src/fetch.py:309-312 (`requested = asked or [built.year]`), api/src/ask.py:371.
   Reproduced two ways with the repo's fixtures:
   (a) question "Median household income in 2015 in US", split report with no `years` (equally: split timed out at SPLIT_WAIT_SECONDS=6, plan_split
       returned None, or the model sent 2015.0 / "2015", which the type filter drops) and the loop stopped before fetch.
       Result: warnings [], vintages [('acs5', 2024)], URL .../data/2024/acs/acs5?... . No warning, no omission reason, no note that a year was asked.
   (b) question "Median household income in the US in 2019", loop itself ran search/resolve/build/fetch_data with years omitted, split report years=[2019].
       Result: warnings [], URL .../2024/acs/acs5. The report's years are consulted only on the finish-fallback fetch (finish.py:367-369, `record.fetch is None
       or fetch_failed`); when the loop already fetched, the requested years (intent.years) and the executed years (record.vintages) are never compared.
   Before this change the question's words were read at the fetch layer too, so (a) and (b) both fetched 2015 / 2019. Now data for the wrong year is
   served with a correct-looking URL and no warning. CLAUDE.md: "Keep requested meaning distinct from execution" and review-pr: "Did anything start
   silently repairing input - a substituted vintage? That is a warning on the answer, never an invisible fix." The design (model supplies years) is
   right; the missing piece is a deterministic requested-vs-executed comparison (intent.years vs record.vintages / fetch.attempted_years) that warns,
   which does not read any question wording. Related: dataset has the same asymmetry only when the report is missing (acs1 request answered from acs5,
   see G6).

G2 [PASS-1, CONFIRMED] Model-supplied years are unbounded, and is_series() iterates the whole span synchronously on the event loop.
   api/src/finish.py:99-100 (`[y for y in years if type(y) is int]`), api/src/vintages.py:60 (`range(ordered[0], ordered[-1] + 1)` with `set(ordered)`
   rebuilt per iteration), called from api/src/fetch.py:322 inside `_arun` (not in a thread).
   Before this change years reaching finish came from `(?:19|20)\d{2}` regexes, so the span was at most ~200 iterations. Now a report with
   years=[10**30, 2022] (an int, so it survives the filter) makes the probe run exceed 120 s and have to be killed; direct measurement of is_series:
   [-1_000_000, 2022] 0.17 s, [-10_000_000, 2022] 2.12 s (linear), so [-10**9, 2022] is about 3.5 minutes and 10**30 does not return. It blocks the
   whole server loop, not just the request. The fetch_data tool's own `years: list[int]` arg already had this exposure from the loop's model, so the
   defect is pre-existing in is_series; this change adds a second, un-gated model channel and removes the regex that bounded it. Fix is at the
   filter (accept only plausible end years, e.g. 1900 <= y <= latest + 1; plan_split already receives `latest`) and/or is_series should not
   materialise the span.

G3 [PASS-1, CONFIRMED] overlapping_vintage no longer fires for a requested series that the planner thins to non-overlapping years.
   api/src/guards.py:131 (`years` now only from record.vintages).
   Probe: report for "every county in Ohio every year from 2017 to 2023" with years 2017..2023, ACS1 ineligible (wildcard): record.vintages
   [('acs5',2017),('acs5',2022)], fetch.omission_reasons ['overlapping_vintage'] x5, response warnings ['acs1_geography_ineligible',
   'geography_level_mismatch'] - no overlapping_vintage. Old code warned from the question's range. This is arguably more truthful (the executed rows do
   not overlap), and the dropped years are still named in fetch.omission_reasons per requirements.md line 17, so it is not a silent short series.
   But the user-visible warning that taught "these 5-year periods share sample" is gone for this path, and the new tests
   (test_guards.py test_consecutive_acs5_vintages_overlap etc.) only exercise the case where all overlapping vintages are fetched, which the thinning
   planner prevents unless allow_overlapping_acs5 is set. Severity is a judgement call for the owner; recorded as NOTE.

G4 [PASS-1, PLAUSIBLE] Prompt wording for `years` can conflict with ACS5 period labels.
   api/src/finish.py:45-47 and api/src/prompts.py:36. "years lists the end year of every vintage the question asks for; a range or an open-ended
   period lists each year through {latest}" reads, for a closed range like "2015-2019 vs 2018-2022", as every year 2015..2022 or every end year 2019..2022,
   not [2019, 2022]. The test (test_ask_loop overlapping_income...) feeds a hand-written [2019, 2022], so it cannot show what the model sends.
   Only E2E can settle this; PLAUSIBLE, not reproducible without a live model.

G5 [PASS-1, CONFIRMED] plan_split's `latest` default is None and renders "through None".
   api/src/finish.py:77 and :87 (`str(latest)`). Only run_ask passes it; test_finish.py calls plan_split(question, complete) without it, so those
   tests exercise a prompt that says "each year through None, the latest published". Not reachable in production today, but a required argument would
   remove the trap. NOTE.

G6 [PASS-1, PLAUSIBLE] A 1-year request is answered from ACS5 silently when the report is missing, and a ResultPlan with no `dataset` now outranks the report.
   api/src/finish.py:321 (`acs1 = intent.dataset == "acs1"`) and api/src/contract.py:256-262 (removed `wants_acs1` flip), contract.py pin_tool_args.
   Split None/timeout means acs1 is never learned from the report; the model's own build_url dataset is then the only source. A client plan that omits
   `dataset` defaults to acs5 and pin_tool_args forces dataset=plan.dataset onto search_tables and build_url, so a report of acs1 and a plan of acs5
   disagree with no warning. In the UI flow the plan always comes from a prior response (dataset populated), so the practical exposure is small.
   My probe with a table-only plan and an acs1 report returned no URL at all with a geography_level_unverified warning; I could not isolate this to the
   plan/report conflict versus the fixture (B19013 under acs1), so PLAUSIBLE. NOTE.

G7 [PASS-1, CONFIRMED] Float or string years are dropped silently.
   api/src/finish.py:100. A report of [2022.0] or ["2022"] keeps nothing (tests test_only_whole_numbers_count_as_the_years... pin this deliberately);
   consequence is G1(a): the latest vintage is served with no warning. Folded into G1's fix (warn when the report mentions years that were not used).
