Findings, most severe first

1. LOW (reproduced; pre-existing at base, but contradicts the fix's stated property)
   scripts/jira_gate_line.py:341 -> :243 -> :169 (copy.deepcopy in edit); also :300-305
   (_is_node), recursive.
   A description nested 124 list levels deep (250 ADF levels) raises RecursionError in
   edit()'s deepcopy, reached from _read_each's changes() call. RecursionError is a
   RuntimeError, outside UNUSABLE (:125) and NO_ANSWER (:127), so it escapes _read_each and
   dry_run. Result: one ticket ends the whole dry run with a traceback, against the commit
   title "one bad ticket ... never takes the run down" and the docstring (:15-16) "a
   document that can be read all the way down". DIR is untouched: the crash comes before
   _discard. The reply still parses at that depth (json.loads succeeds under 3.12), so the
   real client returns it. Measured first failures: changes() at 124 list levels,
   _is_document at 249, _dump at 248. The same RecursionError escapes the base version's
   dry_run. Unverified: whether Jira stores ADF that deep (no live system was used).
   Possible fix: treat RecursionError per ticket as unusable in _read_each, or bound the
   depth in _is_node before edit() runs.

2. LOW (reproduced; documented behaviour, wrong label)
   scripts/jira_gate_line.py:127 (NO_ANSWER includes SystemExit), :342-343, :365-367; compare :617.
   jira_transition._api turns every HTTP error status (404, 403, 429 ...) into SystemExit(1),
   and NO_ANSWER treats that as "no answer". A ticket the search still lists but that was
   deleted or hidden since then gets a 404 on its own read. That stops the whole dry run with
   "nothing changed in DIR: CC-2: no answer from Jira (SystemExit: 1)", although Jira did
   answer. The docstring says the search can lag behind an edit, so the stale entry can block
   every dry run until the index catches up. The apply path handles the same 404 by refusing
   that ticket and going on. Fail-safe, nothing is written, and the docstring says "When the
   search or a read gets no answer, the dry run stops", hence LOW. The HTTP code is printed
   on stderr just above by jira_transition._api, so it can be recovered. Base also stopped
   here, as an uncaught SystemExit.

3. NIT (reproduced)
   scripts/jira_gate_line.py:365-366.
   `except ConnectionError` is meant for _read_each's wrapped errors, but it also catches a
   raw ConnectionError subclass raised by the search. jira_fetch._api converts only HTTPError
   and URLError, so a ConnectionResetError during resp.read() reaches here unconverted. The
   operator then sees "nothing changed in DIR: [Errno 10054] An existing connection was
   forcibly closed", without the "no answer from Jira" framing the other paths give. The exit
   code (1) and DIR are correct.

4. NIT (reproduced)
   scripts/jira_gate_line.py:690.
   main() creates the default folder before the dry run. A run with nothing to write, or one
   that stops, leaves an empty jira-gate-line-* folder in the temporary directory every time.
   On the nothing-to-write path the folder's name is never printed. Two runs left two empty
   folders.

5. NIT (reproduced with the stand-in wording)
   scripts/jira_gate_line.py:301 (_is_node docstring); behaviour in closure.adf_text,
   outside the diff.
   The docstring says what _is_node rejects "would be read as no text", which suggests that
   what it accepts is read in full. adf_text still reads no text from a node of a kind it
   does not know, or from text held in attrs, such as an `expand` node's title. A ticket
   whose only remnant is the contract heading in an expand title is counted clean (exit 0,
   nothing refused). An unknown node kind would not pass Jira's ADF validation; an expand
   with attrs.title is valid ADF. A paragraph body moved alongside it is still caught by
   the marker and sentence checks, so only heading-only remnants slip through. That falls
   inside the documented limit "a copy rewritten in all of those is not recognised".
