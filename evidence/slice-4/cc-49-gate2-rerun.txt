--- Independent manual cold read of web/src/csv.ts end-to-end (not just the diff) ---

  - BOM escape sequence: line 27 is `new Blob(["﻿", csv], ...)`. Confirmed
    this is the six-character JS escape sequence `\`, `u`, `f`, `e`, `f`, `f`
    sitting in source text, not a raw invisible U+FEFF codepoint embedded in
    the file. Confirmed two ways: (a) visual inspection of the Read tool's
    output, which shows the literal backslash-u-f-e-f-f characters; (b) the
    direct byte check below (part of the assignment, not just inspection) —
    `chr(0xfeff) in data` is False for both csv.ts and csv.test.ts. No mistake
    of the kind the task worried about (tool-call escaping turning `﻿`
    into a literal embedded byte) occurred.
  - `document.body.appendChild(anchor).click()` (line 29): `Node.appendChild`
    returns the appended node per the DOM spec, so this is exactly
    `document.body.appendChild(anchor); anchor.click();` in one expression —
    does what it looks like it does, no aliasing or no-op risk.
  - Ordering of `anchor.remove()` (line 30) then `URL.revokeObjectURL(url)`
    (line 31): remove-then-revoke. `.click()` has already run synchronously
    on line 29, so the browser has already read `anchor.href` and initiated
    the download before either cleanup call runs; removing the anchor from
    the DOM does not cancel an already-triggered download, and revoking the
    blob URL after removal doesn't change anything the download needed the
    anchor element for. The two cleanup calls are independent of each other's
    order — swapping them would not change behavior. (The pre-existing
    risk that some older WebKit builds want a delay before revoking a blob
    URL used for a same-tick download is unchanged by this diff — it was
    already an immediate revoke before the fix commit, and is out of this
    fix's scope.)
  - `sanitizeSegment` inlined as `clean` inside `csvFilename` (lines 21-24):
    byte-for-byte the same regex pair (`replace(/[^A-Za-z0-9_-]+/g, "-")` then
    `replace(/^-+|-+$/g, "")`) with the same `|| "export"` fallback, just
    renamed and given function-expression syntax instead of a top-level
    `function` declaration. No behavior change versus the pre-fix version
    reviewed in the first Gate 2 pass — verified by re-deriving
    `csvFilename("../../etc/passwd", "acs5", "")` by hand: non-alnum runs
    `../../ ` and `/` collapse to single dashes, leading dashes strip, giving
    `etc-passwd-acs5-export.csv` — matches csv.test.ts's assertion exactly,
    and matches the pre-fix module-level function's behavior on the same
    input (unit-tested in the first Gate 1 pass).
  - Formula-like-text follow-up (item 3 from the first Gate 2 pass): left
    unescaped, as the fix commit says. Re-read the argument cold rather than
    accepting the commit message: every `DatasetRow` field
    (`dataset, year, period, tableId, variable, geoid, name, estimate, moe,
    universe`) is populated in `web/src/display.ts`'s `normalizeActiveDataset`
    from the Census API response — `name` is the Census `NAME` variable, not
    user-entered text, and no other UI path lets a user type a value that
    flows into a `DatasetRow` before it reaches `rowsToCsv`. Agree this is a
    defensible non-fix: formula-injection escaping guards a boundary
    (user-typed text reaching a spreadsheet) that does not exist here. Not a
    gap; correctly left as a documented follow-up, not a blocker.
