SECTION 2: adversarial-matrix coverage judgment (matrix items -> existing tests)
==============================================================================

Matrix items named for this ticket, and the test that exercises each:

- RFC 4180 quoting of commas/quotes/newlines
    csv.test.ts > rowsToCsv > "writes required headers, then one RFC 4180 row
    per DatasetRow, verbatim" -- fixture NAME field carries a comma, an
    embedded double quote, and an embedded newline together; full-string
    byte-exact assertion.
- verbatim identifier preservation including leading zeros
    csv.test.ts > rowsToCsv > "preserves identifiers with leading zeros
    verbatim, unformatted" -- GEOID "0400000US01", variable "B01001_001E".
- raw unformatted numeric strings
    covered by the same "writes required headers..." test: estimate
    "123456" is asserted verbatim (no thousands separator).
- missing values as empty cells rather than zero/sentinel
    covered by the same test: moe: null renders as an empty CSV cell
    ("123456,,Population...").
- filename sanitization/determinism
    csv.test.ts > csvFilename > "joins table/dataset/vintage, strips unsafe
    characters, falls back on empty fields" -- path-traversal input and an
    empty vintage field both exercised. determinism follows from purity (no
    I/O, no Date/Math.random in csvFilename/rowsToCsv) and was not given a
    separate test.
- post-refinement replacement
    App.plan.test.tsx > "posts a table edit with the original question, not
    rewritten prompt text" -- CSV button title updates from B01003 to B19013
    after a successful table override.
- failed-refinement retention
    App.plan.test.tsx > "keeps the prior result when the override is
    rejected and shows the field error" -- CSV button title still reads
    B01003 after a rejected (422) override. A second test, "keeps the prior
    result when the refinement cannot reach the API", exercises the same
    catch-block code path (network failure instead of validation failure)
    without a CSV assertion; both failure sources hit the identical `catch`
    branch in App.tsx's runAsk (result state is only ever written on the
    success path), so retention is not a second, independently-implemented
    behavior -- one assertion is sufficient to mutation-check it (confirmed
    below, mutation 16).
- no export control with zero rows
    App.test.tsx > "keeps URL and table metadata on Census fetch failure,
    with a visible notice" -- rentFailure fixture has rows: [], and the
    Download CSV button is asserted absent (queryByRole -> null).

Judged gap considered and NOT added: an estimate:null -> empty-cell case
parallel to the existing moe:null case. Same one-line `?? ""` pattern,
already exercised for moe in the primary rowsToCsv test; and mutating that
fallback to a *removal* (dropping `?? ""` entirely) has no observable effect
at all here, since `Array.prototype.join` already coerces `null`/`undefined`
to "" -- confirmed while designing mutation 5, which therefore changes the
fallback's *value* (`?? "0"`) rather than removing it, and that is the
mutation that is actually a real regression risk. A second, symmetric test
for `estimate` would duplicate that same one-line ternary with no new
defect class covered; skipped as low-value, not as a budget dodge (see next
paragraph -- there is no budget room for it either way).

No test was added in this gate. web_src_loc is measured at exactly
3100/3100 on this branch (see SECTION 1) -- zero headroom -- and every
*.ts/*.tsx file counted by scripts/check_budgets.py's `web_files` glob
includes test files, so a new test line would put the branch over budget.
Per CLAUDE.md ("Never raise a budget... say so and ask"), budgets.toml was
left untouched and no new test line was written. Coverage was judged
adequate against the named matrix (above); if a reviewer disagrees on the
estimate:null case, closing it needs either a budget raise (human decision)
or trimming an existing line elsewhere to net zero -- flagged here rather
than done silently.
