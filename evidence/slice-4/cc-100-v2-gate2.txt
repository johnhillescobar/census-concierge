--------------------------------------------------------------------
FINDING 1 — SEVERITY: HIGH (silent wrong answer, confirmed by reproduction)
api/src/ask.py:104-107 (`_absorb`'s geo_queries bookkeeping) interacting with
api/src/finish.py:65-73 (`_wrong_comparison`) and :115-125 (repair args)
--------------------------------------------------------------------

`_absorb` appends the current `query` to `record.geo_queries` on ANY
single-place, non-compare, non-wildcard, non-`places` resolve_geography call
that legally resolves to at least one geography:

    query = str(args.get("query") or "").strip()
    if record.geo_status["compare"] or get("wildcard", False) or args.get("places"):
        record.geo_queries = []
    elif query and record.geographies:
        record.geo_queries.append(query)

This has no way to distinguish "two calls that named two different places
because the model is assembling a comparison one leg at a time" (the
intended repair target) from "two calls that named the SAME logical place,
because the first one was ambiguous and the model refined it with a second,
more specific query" (an ordinary single-place disambiguation, not a
comparison at all). Both produce `len(record.geo_queries) == 2` with
`geo_status["compare"] == False`, which is exactly the trigger
`_wrong_comparison` uses:

    if len(queries) >= 2 and not status.get("compare"):
        return True

Unlike the mechanism this replaces — the old `_wrong_comparison` used
`split_comparison(question)` on the actual question TEXT, so a
non-comparison question could never trigger a "wrong comparison" repair, no
matter how many resolve_geography calls happened — this new count-only check
runs BEFORE any text-based check and does not require the question to look
like a comparison at all. That textual safety net is what this diff removes
for this code path.

Confirmed by reproduction (scratch test against commit 36ef5cc, deleted
afterward, not part of any commit): question "population of Springfield,
Illinois". The model calls resolve_geography("Springfield") — ambiguous,
resolves several candidates, first pick is Springfield, Missouri — then
refines with resolve_geography("Springfield, Illinois"), which resolves
correctly and legally. Both calls are legal, non-wildcard, non-compare,
non-`places`, so both queries land in `record.geo_queries`. The model then
builds the URL and fetches for the (correct) Illinois geography and stops.
`finish_tools` still runs unconditionally (`run_ask` calls it regardless of
whether the model already produced a URL). `_wrong_comparison` returns True
(`len(queries) == 2`, `compare` False) even though the question named one
place and used no comparison language whatsoever. finish then replays
`resolve_geography(places=["Springfield", "Springfield, Illinois"])`, which
legally resolves BOTH as a two-way comparison and overwrites the record:

    response.plan.geographies ==
      [GeoSpec(for_spec='place:70000', name='Springfield city, Missouri', ...),
       GeoSpec(for_spec='place:72000', name='Springfield city, Illinois', ...)]

The final answer is a fabricated two-place comparison between Springfield,
Missouri (the model's own superseded, wrong first guess) and Springfield,
Illinois (the place actually asked about), complete with a `comparisons[]`
MOE_diff entry between two unrelated cities that share a name — for a
question that asked about exactly one place and never suggested a
comparison. This is precisely what docs/playbooks/review-pr.md's
silent-wrong-answer section calls out ("did anything start silently
repairing input... that is a warning on the answer, never an invisible
fix") — here the "repair" itself manufactures the wrong answer, with no
warning distinguishing it from a real comparison.

Not covered by any test in this diff: test_ask_loop.py adds
`test_sequential_single_place_calls_are_repaired_by_finish_tools`, but that
fixture uses two calls for two genuinely different places forming a real
comparison ("Austin city, Texas" then "Dallas city, Texas"). No test in this
diff exercises two sequential single-place calls for the SAME place (an
ambiguous-then-refined lookup), which is the case that breaks.

FINDING 2 — SEVERITY: MEDIUM (crash risk, not silent-wrong-answer)
api/src/contract.py, `take_chart`'s deterministic fallback (~line 405-412)
--------------------------------------------------------------------

The model-supplied chart path guards `ChartSpec` construction:

    if saw:
        try:
            spec = ChartSpec.model_validate(payload)
        except ValidationError:
            unavailable = True

The new deterministic fallback a few lines below builds a title from live
Census `NAME` data and constructs `ChartSpec` directly, with no such guard:

    names = sorted({str(row.get("NAME") or "") for row in rows} - {""})
    by_geo = f"{table_id}: {', '.join(names)}" if names else table_id
    ...
    spec = ChartSpec(type="line", x="year", y="estimate", title=title, series_by=series)
    ...
    spec = ChartSpec(type="bar", x="geography", y="estimate", title=by_geo)

`ChartSpec.title_is_plain_text` rejects any title matching
`_UNSAFE_TITLE = re.compile(r"<[^>]+>|javascript:", re.I)`. Census NAME
values are very unlikely to contain `<` or `javascript:` today, but this is
untrusted external data (fetched live from the Census API) flowing straight
into a validator that the sibling code path treats as fallible, while this
path treats it as infallible. If it ever trips, the `ValidationError`
propagates out of `take_chart` uncaught, which would fail the whole `/ask`
response (no URL, no rows, nothing) instead of degrading to
`chart_unavailable` the way an invalid model-supplied chart does. Low
likelihood, easy fix (wrap in the same try/except), inconsistent as written.

Reviewed and found NOT to be bugs (the four points named in the brief):

- `record.override` interaction: `_absorb`'s resolve_geography branch
  early-returns before touching geo_queries when
  `record.override.geographies` is set — but `dispatch` (api/src/ask.py:272)
  already short-circuits `tool.ainvoke`/`_absorb` entirely in that case
  ("override geography", ok=True, no _absorb call at all), so the early
  return inside `_absorb` is unreachable dead code for that exact condition,
  pre-existing on main, not introduced or worsened by this diff.
- Wildcard-adjacent resolves: `_fail(...)` always threads `wildcard=` through
  on the failure paths that matter (nesting failures), so a failed wildcard
  query still sets `wildcard=True` on the artifact and correctly resets
  `geo_queries`. No stale accumulation across a wildcard boundary.
- `geo.py` `_arun`'s `legs[0] if legs else query` fallback: correct for a
  single-entry `places` list (falls through `sides = split_comparison(query)`
  since `len(legs) < 2`, then resolves `legs[0]`); `args.get("places")` in
  ask.py's reset check is keyed off the raw args dict, not the parsed
  `legs`, so it still resets correctly for a 1-entry list.
- `parentless_tracts(query, ...)` with `query=""` and only `places` set: the
  underlying regex (`_TRACT_VS.search("")`) simply returns no match on an
  empty string; no exception, no incorrect tract-pair detection.
