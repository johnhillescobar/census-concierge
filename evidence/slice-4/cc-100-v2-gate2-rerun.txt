FINDING 1 — SEVERITY: MEDIUM (documented residual limitation is broader,
and more likely to fire, than its own writeup suggests) — NOT BLOCKING,
already disclosed, but the risk assessment should be revisited
api/src/geo.py:160-168 (`track_geo_query`)
--------------------------------------------------------------------

`track_geo_query`'s same-place-refinement detector is a bare case-insensitive
substring check between consecutive single-place queries:

    folded, prior = query.casefold(), queries[-1].casefold()
    if folded in prior or prior in folded:
        return [*queries[:-1], query]   # treat as a refinement, drop the leg

The fix commit's own "Known residual limitation" note names exactly one
false-positive case ("Texas" vs "Texas City") and judges it "rare." Checked
computationally (casefold containment, the actual runtime check):

    Texas      | Texas City         -> True (already documented)
    New York   | New York City, NY  -> True
    Washington | Washington, D.C.   -> True
    Washington | Washington, DC     -> True
    Kansas     | Kansas City, MO    -> True
    Orange     | Orange County, CA -> True

Two of these are materially more likely to occur than the documented case:

- "New York" vs "New York City, NY" is not an edge case for this project —
  "population of New York City" is CLAUDE.md's own running example of the
  question the predecessor system failed to answer. If a model sequentially
  resolves "New York" (ambiguous: state or the city sharing its name) then
  "New York City, NY" (disambiguating), that is genuinely a refinement and
  the collapse is correct. But if a user asks to compare New York State
  against New York City specifically — an extremely ordinary Census-literacy
  question for this product's own audience — and the model resolves the two
  legs with sequential single-place calls (rather than one `places` call, as
  `prompts.py`'s new instruction asks but does not force), the second leg is
  silently dropped and the answer becomes "New York City" alone, with no
  warning distinguishing this from an intentional disambiguation. This is
  the same failure shape as the fix commit's own Finding 1
  (fabricated/collapsed comparison, no warning) reintroduced by the fix for
  Finding 1.
- "Washington" vs "Washington, D.C." has the same shape, and DC-vs-state
  collisions are already known sensitive ground in this codebase (`geo.py`
  imports `token_is_dc` specifically for this class of ambiguity elsewhere).
- The city/containing-county case ("Orange" vs "Orange County, CA",
  "Baltimore" vs "Baltimore County") is directly relevant to this project's
  stated audience (GIS professionals routinely need place-vs-county
  comparisons) though less likely to arise via sequential single-place calls
  than via a batched `places` call (which bypasses `track_geo_query`
  entirely).

This is not a new bug introduced carelessly — it is the same accepted
trade-off already named and accepted in FIXES APPLIED, and the fix's own
design note is explicit that it is a heuristic over tool-call strings, not
prose, by design (AC9's constraint). It is reported here because "rare" is
doing more work in the acceptance rationale than the evidence supports: at
least one of the collision pairs is the project's own flagship example
query, not a corner case. Recommend either (a) expanding the residual-
limitation note to name New York/Washington explicitly (so a future AC12
manual pass knows to check them), or (b) tightening the heuristic to require
the shorter string plus ", <state/abbrev>" as a suffix of the longer one
(which still collapses "Springfield" -> "Springfield, Illinois" but would
no longer collapse "New York" -> "New York City, NY", since "City, NY" is
not the state suffix of "New York"). Not blocking this Gate 2 pass — this is
the second re-run permitted by the playbook, and the finding is a scope
correction to an already-disclosed, already-accepted limitation, not an
undisclosed one.
