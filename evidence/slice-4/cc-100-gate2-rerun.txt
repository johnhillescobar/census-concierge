--- NEW findings from this re-run (not in the original gate2.txt) ---

3-NEW-1. [Blocking -- silent-wrong-answer, found independently by both this
reviewer and the code-review skill] Requiring a leading comma before the
bare-state alternative (`,\s*\b(?:{_STATE_ALT})\b`) breaks bare
state-vs-state comparisons joined by "and"/comma with no place name and no
comma before the first state -- a shape that worked correctly before this
commit. Verified directly:

  git worktree (51a3608, pre-a92adc7):
    split_comparison("Compare the population of Georgia and Alabama since 2019.")
      -> ['Compare the population of Georgia', 'Alabama']   (correct, 2 clauses)

  a92adc7 as committed:
    split_comparison("Compare the population of Georgia and Alabama since 2019.")
      -> None
    split_comparison("Compare the population of Texas and Oklahoma since 2019.")
      -> None
    split_comparison("Compare the population of Ohio and Indiana since 2019.")
      -> None
    split_comparison("Compare median income in California and Texas since 2019.")
      -> None
    split_comparison("Compare Texas, Ohio, and Illinois since 2019.")
      -> None   (bare-state LIST also affected, not just pairs -- code-review's
                 second example, independently reproduced)

Traced the consequence end-to-end, not just the regex return value:
- `ResolveGeographyTool._arun` (geo.py:223-240): when `split_comparison`
  returns None, it falls through to `self._resolve(query, ...)` on the WHOLE
  original question text as a single geography lookup.
- `find_state("Compare the population of Georgia and Alabama since 2019.")`
  returns `('alabama', '01')` -- confirmed live -- i.e. it silently keeps only
  the second-mentioned state.
- The single-geography path (geo.py:294-306) then returns one legal `state`
  spec for Alabama with `compare=False` -- there is no comparison flag, no
  `ambiguous_place` warning, no dropped-place signal of any kind. Georgia is
  gone from the response with nothing on the record to indicate a comparison
  was ever attempted.
- `finish.py:_wrong_comparison` (line 65-70) cannot redo this either:
  `sides = split_comparison(question); if sides is None: return False` --
  the same None return that broke the direct-resolve path also disables the
  finish-time repair path, for the same reason.

This reproduces CC-100's own original bug class ("and"-phrased comparison
silently drops every place but one, no warning") for a plausible, common
input shape this ticket's own scope explicitly claims to cover ("'and'/a
comma list" per docs/ask-path.md) -- bare US-state-vs-state comparisons with
no leading comma and no place-level qualifier. "versus"/"compared to"
phrasing for the same states is unaffected (`_VERSUS` is tried first and
does not depend on `_STATE_CLAUSE_END`); only the "and"/comma-list path is
affected. No test in the diff, and no golden-set/demo question, exercises a
bare state-vs-state "and" comparison, so this shipped undetected by every
machine check that ran green.

3-NEW-2. [Non-blocking, narrow -- silent malformed clauses] The `(?!\w)`
lookahead added to `_DC_NAMES` "so an optional period doesn't force a
backtrack" still backtracks when a DC clause is immediately followed by a
word character with no separating space (e.g. no space before "and").
Reproduced directly:

  split_comparison("Compare the population of Washington, D.C.and Seattle "
                    "city, Washington since 2019.")
    -> ['Compare the population of Washington, D.C', '.and Seattle city, Washington']

Clause 1 loses its trailing period; clause 2 gains a stray leading `.` and no
separating space -- both malformed geography queries handed to `_resolve`.
Narrower than 3-NEW-1 (requires no space before "and", an unusual but not
impossible typo/model-output shape) and contradicts the stated purpose of
the `(?!\w)` change. No test covers this shape either.

3-NEW-3. [Non-blocking, resource waste] `asyncio.gather(*(self._resolve(side,
...) for side in sides))` (geo.py:225, no `return_exceptions=True`) does not
cancel sibling legs when one leg's coroutine raises. `_resolve` reaches
`list_census_names` via `await asyncio.to_thread(self.list_geographies, ...)`
(geo_list.py), a real live Census HTTP call; per Python's documented
`asyncio.gather` behavior (confirmed against the library, not assumed): on a
raised exception with `return_exceptions=False` (the default here), the
other awaitables are not cancelled and keep running with their results
discarded. A failed leg in an N-way comparison now costs up to N wasted live
Census calls instead of the old sequential comprehension's short-circuit
after the first failure. Not a correctness bug (the caller still sees the
exception) and bounded by N (small), but a real latency/traffic regression
for the failure path of exactly the feature this ticket adds.

3-NEW-4. [Minor, code quality, drift risk] `_DC_NAMES` in geo.py duplicates
logic that `api/src/geo_list.py`'s existing `_DC` regex (confirmed present,
geo_list.py:67) and `find_state` already solve for the identical
"Washington, D.C. must win over the state named Washington" ambiguity --
`find_state` is even imported into geo.py already (line 18) but not reused
for this boundary regex. Two independently-maintained DC patterns can now
drift (one already has the 3-NEW-2 backtrack bug the other does not).

3-NEW-5 (restates 4, sharper): the `compare_count` fallback-default idiom is
duplicated across five call sites (see Finding 4 above) rather than one
shared accessor. Values agree today; a sixth or seventh caller guessing a
different default would reintroduce the exact bug class this ticket exists
to close, with no single place to catch it.
