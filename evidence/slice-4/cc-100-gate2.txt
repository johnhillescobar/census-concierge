FINDINGS (Gate 2, both passes combined)
====================================================================

1. [Functional -- reintroduces the bug class CC-100 fixes, via the override
   path] `apply_override` in api/src/contract.py:243-263 sets
   `geo_status["compare"]` but never sets `"compare_count"`. Every downstream
   reader of `geo_status.compare_count` was updated by this diff to key off
   that field, but all three fall back to a hardcoded default when it is
   missing, and the defaults do not even agree with each other:
     - api/src/ask.py:366 (fetch_data.last_geographies) and
       api/src/contract.py:198 (plan_from_record) default to 2.
     - api/src/guards.py:217 (ambiguous_place) defaults to 0.
   Reproduced directly: an AskRequest.plan override carrying 3 geographies
   (e.g. re-running an edited plan strip for an Austin/Houston/San Antonio
   comparison -- the "editable plan strip; re-run on override" feature named
   in .claude/PLAN.md, already shipped as CC-89) has record.geographies with
   all 3 entries, but plan_from_record() and the fetch fan-out both truncate
   to 2 (confirmed by direct execution: `plan_from_record` returns 2
   geographies, and the fetch tool's `last_geographies()` slice is length 2,
   for a 3-geography override). Separately, guards.py's 0-default means
   `ambiguous_place`'s early-return never fires for this same override, so a
   clean 3-way override also gets a spurious ambiguous_place warning. No
   warning is raised for the truncation itself -- the drop is invisible,
   which is exactly what CLAUDE.md's "silently repairing input" trap warns
   against, and exactly the failure class this ticket exists to close.

2. [Functional, untested -- degrades the new comparison feature for a common
   class of real place names] `split_comparison`'s state-anchored "and"/
   comma-list splitting in api/src/geo.py over- or mis-splits whenever a
   compared place's own name is, or contains, a US state name. Confirmed by
   direct execution:
     - "Kansas City, Kansas and St. Louis city, Missouri" ->
       ['...Kansas', 'City, Kansas', 'St. Louis city, Missouri'] (3 malformed
       clauses instead of 2).
     - "Washington, D.C. and Seattle city, Washington" ->
       ['...Washington', 'D.C. and Seattle city, Washington'] (clause 1 loses
       ", D.C."; clause 2 is garbled).
     - Same failure for "Delaware, Ohio", "Indiana, Pennsylvania", and
       "New York city, New York and Boston city, Massachusetts".
   Root cause: `_STATE_CLAUSE_END = re.compile(rf"\b(?:{_STATE_ALT}|{_DC_NAMES})\b", ...)`
   puts `_STATE_ALT` (which already contains the literal "washington") ahead
   of `_DC_NAMES` in the alternation. Python's `|` is first-match-wins per
   start position, not longest-match, so the bare "washington" branch always
   wins before the "washington, d.c." branch is ever tried -- making the new
   `_DC_NAMES` alternatives for the comma/space-joined "Washington D.C." form
   dead code. `api/src/geo_list.py`'s existing `find_state`/DC handling
   already solved this exact ordering hazard elsewhere in the codebase (its
   own DC regex is tried and matched correctly, per
   `test_find_state_recognizes_dc_before_the_state_named_washington`-style
   coverage in test_ask_tools.py's find_state tests), but that solution was
   not reused for the new clause-boundary regex. Since a place-per-clause
   that fails to resolve legally falls out of the "all(hit.legal and
   hit.specs for hit in hits)" check in ResolveGeographyTool._arun, this
   over-splitting is likely to fall back to keeping only the first
   successfully-resolved single leg -- i.e. it can regress into the original
   "drops every place but one" bug for this whole class of place names, most
   notably "Washington, D.C.", an extremely common comparison target. No
   test in this diff exercises a state-named place, or DC, as one leg of an
   "and"/comma comparison.

3. [Non-blocking, latency] `ResolveGeographyTool._arun` resolves N-way
   comparison legs sequentially: `hits = [(await self._resolve(side, None,
   dataset, year, entries))[1] for side in sides]` (api/src/geo.py:221) awaits
   each leg in turn rather than concurrently (e.g. `asyncio.gather`). Each
   leg's `_resolve` can call `list_census_names`, a real live `httpx.get`
   against the Census API (api/src/geo_list.py:206-209), so a 3+-way
   comparison -- the feature this diff newly supports -- now costs roughly N
   sequential Census round-trips where the pre-existing 2-way "versus" path
   cost 2. p95 latency is already measured at 17.955s against a 20s budget
   ceiling (budgets.toml), so this is a real latency risk for exactly the
   multi-place case this ticket adds, not a theoretical one. Not a
   correctness bug and not blocking Gate 2, but worth a follow-up.

4. [Minor, code quality] The `int(status.get("compare_count") or 2)` /
   `int(status.get("compare_count", 0) or 0)` fallback idiom is copy-pasted
   across api/src/ask.py:366, api/src/contract.py:198, and
   api/src/guards.py:217 with two different, uncoordinated default literals
   (2 in the first two, 0 in the third). This duplication is the direct
   mechanical cause of finding 1 shipping unnoticed -- a single shared
   accessor (or making the field non-optional wherever geo_status is
   constructed) would have surfaced the apply_override gap immediately.

5. [Minor, non-blocking, unverified by tests] finish.py's widened fetch
   retry gate (`record.fetch is None or not record.fetch.ok`, api/src/finish.py:141)
   fires on ANY failed main-loop fetch, not only the comparison-repair case
   it was written for. For a genuinely non-recoverable failure (bad
   variable/table combination, persistent upstream error), finish_tools now
   always issues one extra, identical, live Census fetch call before giving
   up -- doubling Census API traffic and latency on every hard fetch
   failure, where before this diff it did not retry at all in that case. This
   is bounded (finish_tools runs once per request, not a loop) and the two
   intended cases are tested (test_finish.py: retry recovers a genuinely
   fixable failure; a successful fetch is never re-fetched), but no test
   covers a failure that is retried and still fails, so the extra live call
   in that branch is unverified by this diff's test suite.
