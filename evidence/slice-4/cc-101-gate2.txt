Verified clean (no bug):

  enumerate(names) if not (picks[i][1].legal and picks[i][1].specs)]` pairs
  each name with its own result correctly.
- `parent_override` threads through every read of `parent_text` in
  `_resolve()` -- it is assigned once (`parent_text = parent_override or
  (wildcard_match.group(2) if wildcard_match else query)`) and every
  downstream use (`find_state(parent_text)`, `detect_level(parent_text)`,
  `place_token(parent_text, ...)`, the two `_fail(...)` messages, and the
  `us = re.search(..., parent_text, ...)` check) reads that same local, so
  there is no path that silently falls back to the original `query` text.

  `.specs`, not `.legal` alone. This matters: `_resolve()`'s final
  `named_rows` matching branch (unrelated pre-existing code, not reachable
  from the wildcard-parent branch since `wildcard_match` is always truthy
  there) can return `legal=True` with `specs=[]` for a bare place-name miss.
  Because `bad`'s check is defensively `legal and specs`, that quirk cannot
  produce a false negative here even though it's a latent trap for a future
  caller of `_resolve()`.
- WILDCARD/WITHIN regex relocation: `git grep -n "_WILDCARD\|_WITHIN"` against
  the branch tree returns no hits anywhere in `api/`. All three usage sites
  (`_nation()`, the new `_arun` gate, and `_resolve`'s `wildcard_match` line)

  ahead of the `legs`/`split_comparison` branch, so when both are

Findings (non-blocking, but real):

1. Every per-parent wildcard leg gets an identical `GeoSpec.name`. In the
   wildcard-spec-building block of `_resolve()` (unchanged code, now called
   once per parent), `spec.name = query.strip()` -- the full original
   question text, not scoped to the parent being resolved. For "all counties
   in Texas and Louisiana" with parents=["Texas","Louisiana"], both resulting
   specs get `name="all counties in Texas and Louisiana"`. `for_spec`/
   `in_spec` still differ correctly (state FIPS differs), so the URL and data
   are correct -- this is not a silent-wrong-answer. But `ambiguous_place`'s
   fallback formatting (`row.name or f"{row.for_spec} {row.in_spec}"`) and
   the frontend's geography picker (`docs/ask-path.md`: "Geography is a
   picker over returned GeoSpecs") both read `.name` as the human label, so a
   user looking at the plan strip cannot visually tell the Texas leg from the
   Louisiana leg apart by name -- only by clicking in to see `for_spec`/
   `in_spec`. Worth a follow-up to set `spec.name` from the resolved parent
   (e.g. "all counties in Texas") rather than the shared raw query.

2. The `parents` field's Pydantic description and the `prompts.py` ROLE
   addition only demonstrate the "in" connector: `"all counties in Texas and
   Louisiana"` / `"each parent as it reads after 'in'"`. The code correctly
   handles the WITHIN-phrased case too (`WILDCARD.search(query) or
   WITHIN.search(query)`, mutation-checked via
   `test_counties_within_two_states_also_resolves_both`), but nothing in the
   prompt or field description tells the model that "counties within Texas
   and Louisiana" also needs `parents` populated. A model that pattern-matches
   the example literally may never populate `parents` for "within"-phrased
   multi-state wildcards, silently falling through to the pre-CC-101
   last-match collapse for that one connector -- mechanically fixed, but
   possibly unreachable in practice depending on how literally the model
   reads the two-sentence hint. This is exactly the kind of gap AC16's
   "varying connectors" test list is meant to catch at PR time; flagging it
   here since nothing in this diff verifies real model behavior against the
   WITHIN phrasing (Gate 1's test calls the tool directly with `parents`
   already supplied, which proves the code path, not the prompt).

3. Minor, cosmetic: `_fail(f"unresolved wildcard parent(s): {', '.join(bad)}"
   ...)` joins raw parent names with ", ". If a parent name itself contained
   a comma (e.g. a malformed model output), the resulting detail string would
   be ambiguous about parent boundaries. No security/redaction concern (these
   are place names, never touch `&key=`), and not reachable through normal
   "Place, ST" canonicalization prompted elsewhere, but worth a one-line note
   since the prompt explicitly asks for bare state names here, not "Place,
   ST" pairs, so there's slightly less structural guarantee than the
   `places` field enjoys.

4. Minor: duplicate parent names (e.g. a hypothetical `parents=["Texas",
   "Texas"]`) are not deduplicated before the `asyncio.gather` fan-out --
   produces two identical legs rather than an error or a merge. Unlikely in
   practice and not a correctness bug (the duplicate leg is still correct
   data, just redundant), so not blocking.
